# 代码组织约定（通用）

适用于所有技术栈。各技术栈的文件（`tanstack-start.md`、`nestjs.md`、`fastapi.md`、`android.md`、`ios.md`）在此基础上补充目录与框架细节。目标是可读、解耦、职责分明；原则取自 Clean Code、SOLID 和各框架官方推荐，只保留在这些仓库里实际用得上的部分。

## 分层与依赖方向

- 按领域分目录，再在领域内按职责分层：界面 → 状态/流程 → 数据访问 → 外部服务。上层可以依赖下层，下层不反向依赖上层，同层领域之间不互相引用内部文件。
- 跨领域复用的代码放公共层（`lib/`、`common/`、`utils/`），公共层不依赖任何具体领域。
- 入口层（路由、controller、页面）只做组装：取参数、调用下层、返回或渲染结果，不写业务规则和 SQL。
- 外部依赖（数据库、HTTP、第三方 SDK）收在一个数据访问层后面，业务代码不直接拼请求或 SQL。

## 单一职责与拆分

- 一个文件、一个函数只做一件事。能用一句话说清它做什么，且这句话里没有「和」，就是合适的粒度。
- 可读性阈值由 lint 检查（单文件 400 行、函数 60 行、圈复杂度 10）。超过时按职责拆分，不要为了过线把一段逻辑切成没有意义的几段。
- 纯逻辑（参数转换、规则判断、格式化、SQL 片段生成）从组件或 handler 里抽成纯函数，配单元测试；有副作用的部分留在外层。参考：console `src/features/admin/hooks/admin-list-table-state.ts`、backend `src/admin/utils/admin-list-query.ts`。

## 抽象与复用

- 同样的结构出现第三次时再抽通用实现；两处相似先保持重复，避免过早抽象。
- 通用实现 + 每个领域一份配置：差异通过配置项、取数函数或渲染函数传入，不用一串布尔开关控制分支。参考：www `src/features/learning/common/learning-list-page.tsx` 与各学科 `*-list-config.tsx`，console `src/features/admin/hooks/use-admin-list-table.ts`。
- 抽通用实现时行为要与原实现逐项一致；确有差异的写进 PR 说明。
- 跨项目不抽共享业务库，只共享 dev-config（见 `GOVERNANCE.md` 复用边界）。

## 常量、类型与配置

- 常量就近定义：只在一个文件用的放文件顶部；领域内共用的放该领域的 `constants`；跨领域的放公共层。不要建一个装下所有常量的全局文件。
- 每个领域的数据类型只定义一份（领域内的 `types`），组件、接口、列定义都从这里引用。前后端共享的类型以 OpenAPI 生成为准，不手写第二份。
- 查询 key、请求选项、路由路径等会被多处引用的标识集中定义一处。参考：www `src/features/notes/query.ts`。
- 环境变量只在配置模块里读取一次并做校验，其余代码从配置模块取值。
- 大体量静态数据放 JSON 或数据库，按需加载，不写成源码。参考：www `src/lib/learning/hanzi/data/levels.ts`。

## 命名

- 名字说明意图而不是实现：`fetchPhysicsPage`、`toOrderByClause`，不用 `handleData`、`util2`。
- 布尔值用 `is` / `has` / `can` 开头；事件处理用 `on` / `handle`；取数用 `fetch` / `get` / `load`，并保持同一仓库内一致。
- 文件名与主要导出一致；同一仓库保持一种大小写风格（前端 kebab-case，Swift / Kotlin 按语言惯例）。

## 错误处理

- 错误在能处理它的那一层处理；下层只抛出带上下文的错误，不吞掉，也不在每一层重复记录日志。
- 同一类错误的映射（HTTP 状态码 → 提示文案、网络异常 → 统一结果类型）集中在一处。参考：iOS `lattefx/Services/Network/NetworkExtensions.swift` 的 `safeApiCall`。
- 日志不打印 token、Cookie、密码、验证码等敏感字段。
- 拼进 SQL 或命令的标识符（排序字段、表名）一律走白名单或格式校验，值一律参数化。

## 注释

- 注释写「为什么」和不明显的约束（兼容历史数据、为了与旧实现一致、某个框架的坑），不复述代码在做什么。
- 不留注释掉的代码和过期的 TODO；需要以后做的事记进待办，不留在代码里。

## 重构方式

- 改到哪个模块整理到哪个模块，每个 PR 只做一件事，可以单独审查和回滚。
- 先确认有测试或可对比的产物（单测、E2E、预渲染 HTML、请求记录）覆盖要改的行为，再动手。
- 删除前先确认没有引用（knip / vulture / 全文搜索），被取代的实现删干净，不留兼容分支。
